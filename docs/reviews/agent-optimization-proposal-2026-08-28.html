Architecture decision proposal · v1

从链接提交器，
到统一任务 Agent

用户说清想解决的问题，Agent 判断是否需要处理视频、按需查证，并在内容就绪后完成最初的请求。创建任务与继续追问，不再是两条割裂的产品路径。

核验日期：2026-08-28 · 范围：创建任务 / 内容理解 / 后续问答 / 本地开发
本轮仅交付方案；未修改业务代码、数据库或部署，未调用付费模型。

01 / DECISION

重构 Agent 层，保留可靠执行底座

推荐：一个任务 Agent，两个执行环境，一套业务工具与云端状态。

线上继续使用 AI SDK 的 ToolLoopAgent + OpenRouter；本地通过官方 Codex SDK / App Server 接入。Agent 决定行动，FastAPI 与 Postgres 决定行动能否被执行，PGMQ 负责长任务及完成后的恢复。

  • 移除自然语言输入中的 URL 自动旁路。有链接不等于用户授权立即处理。纯链接可采用明确的默认产品约定，但也进入同一 Agent 入口。
  • 采用 Agentic Retrieval。模型可以不检索、搜索、改写查询、补读上下文；不强制“先检索一次再回答”，也不把所有问题都变成长工具链。
  • 补齐异步恢复。视频处理成功不是用户请求完成；需要回答原始问题时，服务器应恢复 Agent，而不是等待用户再问一遍。
  • 不自研通用 Agent 框架。复用官方循环、协议与事件；只实现产品必须持有的权限、行动回执和恢复状态。

本方案替代此前“以 2-step RAG 作为产品总架构”和“优先采用社区 Codex provider”的建议。也不把“本地 Codex vs OpenRouter 谁回答更好”设为重构前置条件。

本次最小完整版本

同一会话理解需求 → 必要时澄清 → 创建一个视频任务 → 异步返回 → 按用户要求回答 → 有依据地追问。允许会话后续关联其他任务，但首版不承诺多视频并行研究。

明确不做

不重写下载 / 转写管道；不迁移供应侧任务；不引入多 Agent、任意代码执行、全网研究、另一套数据库或消息系统；不为“先进”而增加向量服务。

02 / VERIFIED GAPS

当前问题不是 SDK 太旧，而是链路没有闭合

仓库已经声明 AI SDK ^7.0.47，线上聊天代码也已使用 ToolLoopAgent。真正需要替换的是入口语义和任务生命周期，不是再升级一次 SDK。

当前机制源码中的事实用户影响 / 改造方向
遇到 URL 就提交ChatContainer 提取 URL 后进入 direct-submit，不经过 Agent。“先别处理这个链接”也会进入提交分支。让 Agent 判断意图，后端继续校验 URL 与权限。
Agent 只能查询工具注册只有 get_task_status、get_task_outputs，没有创建任务工具。聊天与真正的任务执行割裂。增加窄粒度业务工具，不让模型操作数据库。
请求保存了，但未被执行output_intent 保存原话、深度、受众；主摘要调用只传原文、目标语言、追踪信息。“重点分析商业模式”没有进入该摘要调用。保留通用内容产物，由恢复后的 Agent 回答私人目标。
完成只更新卡片TaskDataGroup 通过 Realtime 更新摘要 / 音频；当前未见服务端 Agent 完成续跑链路。用户还得主动追问才能获得针对性回答。增加持久化的完成事件与一次有界续跑。
提交与会话分开保存direct-submit 先调用后端入队，再单独 upsert 聊天消息与线程关联。后半段失败可出现“任务已创建、聊天未关联”。在命令事务中保存行动回执与关联。
上下文靠硬截断摘要 / 历史有字符预算；原文用关键词分块打分；跨语言无命中会偏向开头。有预算不等于能找到证据。需要可继续导航的原文引用、搜索与读取工具。
本地不是同等能力官方 Python SDK 已在用，但当前桥接只接收拼好的文本，并明确禁止工具。本地“能回答”不能代表生产 Agent 链路已验证。统一业务工具契约，而非伪装成同一种模型。

以上是当前工作区的静态代码结论，不是线上故障率、延迟或质量测量；原始截图中的服务不可达仍需按具体运行日志单独验收。

03 / TECHNOLOGY CHOICE

没有通用“最好”，有适合当前边界的选择

采用的行业原则是：成熟 Agent 循环 + 独立业务工具 + 外置持久化状态。OpenAI 2026-08-19 的官方文章明确讨论把 Codex harness 嵌入产品；Anthropic 2026-04-08 的工程文章也强调把推理、执行与会话分开。它们支持这一分层，不意味着 VibeDigest 必须复制其整套基础设施。[OpenAI · Anthropic]

候选价值代价与决策
ToolLoopAgent
+ 现有 PGMQ		已有 UI / tool stream 可复用；OpenRouter 路径不变；沿用云端状态与执行管道。推荐首版。新增任务级恢复点；不提供每一步模型循环的持久化 checkpoint。中断时重跑有界只读推理，副作用靠回执幂等。
WorkflowAgent官方持久化 Agent；工具步骤重试、长等待与审批恢复能力更完整。不是“不够先进”，而是会引入额外执行 / 持久化机制及跨系统完成通知。若需要多次长等待、长审批或精确逐步恢复，优先重新评估它，停止扩张自写状态机。
HarnessAgent
+ Codex adapter		官方维护的 AI SDK harness 集成，可投影到现有 UI stream。当前文档明确 experimental；Codex adapter 的内置工具过滤 / 审批也有能力限制。不作为要求稳定的本地订阅接入基线。
把全部 Agent 搬到 Python与现有后台 worker 同语言，恢复执行可更直接。需要迁移当前 TS Agent、流协议与工具边界。只有跨语言调用成为实测瓶颈时再比较；本轮没有证据支持全量搬迁。

依据：AI SDK 7 发布说明（2026-06-25）、WorkflowAgent 文档、Harness 文档；同时核对了仓库已安装包的对应 docs。选择 PGMQ 是针对当前产品与仓库约束的判断，不是官方声称它比 WorkflowAgent 更好。

复杂度止损线：首版最多“提交一次长任务 → 完成后恢复一次回答”。如果实现开始需要通用 DAG、任意暂停点或自行重建每一步工具日志回放，应停止该方向，提新的 ADR 比较 WorkflowAgent，而不是继续造框架。
04 / TARGET EXPERIENCE

一个会话，跨越任务创建与内容理解

示例：“帮我看这个访谈，重点讲它的商业模式，用中文；没提到的数据不要补。”

  1. 理解请求Agent 读取当前会话、链接与明确要求；需要澄清时只问必要问题。
  2. 提交工具调用 create_video_task；后端鉴权、检查额度、去重并原子入队。
  3. 立即交接回传已确认的 task_id 与状态；展示一张任务卡，释放聊天连接。
  4. 后台处理原有 worker 完成抓取、转写和通用摘要；用户可以离开页面。
  5. 恢复原目标完成事件唤醒 Agent；读取最新目标与证据，回答商业模式，而非再发一份通用摘要。
  6. 继续追问同一 Agent 根据新问题决定直接解释、补查原文或明确材料不足。
层持有的职责不负责
聊天 UI输入、流式回答、任务卡、引用、错误恢复；订阅数据库更新。不靠 URL 正则决定付费行动；不承担后台 Agent 唤醒。
应用 Agent理解意图、澄清、选择工具、补充检索、解释证据与完成目标。不决定 owner、额度、执行环境或队列；不运行下载 / 转写。
业务工具层窄契约、权限校验、输出裁剪、行动幂等；绑定服务器提供的调用身份。不复制一套“固定问答流程”；不信任模型传来的 user_id。
FastAPI + Postgres权威命令、任务 / 行动 / 会话关联、状态转换、原子 enqueue。不在 HTTP 请求里等整段视频处理完。
PGMQ + worker已有长任务；新增有界 Agent 恢复 job 的派发、租约和重试。不把 Realtime 通知当可靠队列；不新增另一份任务真相。

direct-submit 怎么处理

删除它在自然语言聊天中的自动分流职责。迁移期保留接口兼容和明确的“提交链接”命令，但底层都调用同一个 canonical submission 服务。新工具不要转调当前 direct-submit 路由，否则会重复生成用户 / 助手消息。旧前端 hook 在新链路验收后再删除。

“统一 Agent”是统一产品能力、业务契约和会话状态，不是假定 Codex harness 与 ToolLoopAgent 有相同的内部推理过程。

05 / TOOLS & CONTEXT

把确定性放在工具边界，把判断留给 Agent

工具模型可提供服务器约束 / 返回
create_video_task候选 URL、目标语言、对用户目标的理解。原始消息为私有真相；owner、thread、稳定 action key 由服务端绑定。返回 task_id、created / reused、状态或明确错误。
get_task_status当前可访问的任务引用。返回状态、进度、失败类型；不允许模型循环轮询等待视频完成。
get_task_context任务引用、需要的摘要语言。返回摘要、来源信息、可用章节 / 时间范围、证据索引；不默认返回所有输出。
search_source问题、改写后的检索词、必要的语言提示。仅检索获准来源；返回稳定片段 ID、内部短摘录、时间戳与是否有更多结果。无命中如实返回。
read_source片段 ID 或受限时间范围。按预算补读相邻片段；验证片段属于获准任务，不开放任意文件 / URL 读取。

工具名称是建议契约，不是本轮已实现 API。首版不添加“规划工具”“自我反思工具”或任意 SQL / shell 工具；澄清直接通过正常对话完成。

上下文按需加载，而不是把原文全塞进 prompt

  • 默认上下文：当前明确目标、最近必要对话、已绑定任务状态、小型内容导航。相同内容只放一次。
  • 短问题可直接基于已有可靠上下文回答；具体事实需要查证时，由 Agent 搜索、改写语言、补读前后段。
  • 不要把“前 18,000 字符”当搜索结果。先有带版本和时间戳的片段索引；跨语言检索失败必须显式暴露，不能悄悄回退成原文开头。
  • 按模型窗口设输入 / 输出 / 工具结果总预算，工具调用与返回成对保留。已截断、未覆盖、无匹配要有结构化标记。
  • 先验证片段导航和查询改写是否满足样本；若跨语言或语义召回仍不达标，再在现有 Postgres 内引入合适索引 / embedding。不要先上新向量平台。

原文、个性化目标与公共内容分开

原文只能作为内部检索材料。面向浏览器的 tool stream、持久化聊天 parts 和公开 HTTP 响应都必须使用安全投影，只包含必要引用、概括与来源链接；不能因为 UI 没展示，就认为原文没有泄露。保留当前公共质量投影与所有权规则。

通用摘要仍是可复用内容产物。个人目标保存在私有会话 / turn 中，最终针对性回答写入该会话，不把投资假设、个人背景等私有要求写进公共摘要。来源中的指令不产生任何行动权限。

06 / DURABLE HANDOFF

最需要补上的，是“交接后还能接着做”

普通 ToolLoopAgent 的执行位于内存中。仅使用它加上 Realtime，不会自动获得断线恢复或后台续跑。本方案只新增产品任务级恢复点，不声称实现了完整持久化 Agent runtime。[官方能力区别]

accepted → running → waiting_task → finalizing → completed
旁支：failed / cancelled。任务 task 的状态与用户请求 turn 的状态分别保存。

最小数据增量

沿用 chat_threads、chat_messages、tasks、task_outputs 与 queue job。新增逻辑上的 agent_turns（原始消息引用、目标版本、状态、任务引用、模型配置、最终消息 ID）与 agent_actions（稳定操作键、命令参数指纹、task_id、执行回执）。准确表名与字段在迁移设计时确定；不创建一套通用事件平台。

  1. 先接受请求，再执行副作用。持久化受鉴权的输入 turn；创建任务工具在同一 Postgres 命令事务里完成 quota / dedupe / task / queue / action receipt / thread binding。失败整体回滚。
  2. 幂等键不是模型生成的 toolCallId。首版每个用户 turn 最多一个创建操作，服务端根据该 turn 的固定操作槽生成键；相同键参数不同必须拒绝。断网重试返回原回执，不再次扣费或入队。
  3. 注册等待与检查任务状态原子进行。如果复用的任务已经完成，立即产生恢复 job；否则登记等待。避免“任务先完成，订阅后注册”的丢事件窗口。
  4. 终态写入与恢复入队在同一事务。视频成功或最终失败都让等待 turn 收到可恢复事件。以 turn + 目标版本 + 完成事件去重；禁止依赖浏览器在线或临时回调。
  5. 复用现有 worker 派发恢复。增加 capability-locked 的恢复 job 类型；可用同一 PGMQ 内的独立优先队列，避免排在大量长视频后面。先复用进程，不预建独立服务或多 worker 协调平台。
  6. 在同一 TS Agent 模块里续跑。worker 调用固定的、服务端鉴权的内部执行入口。只传 run / job ID，入口读取权威状态并重新检查用户权限；不存用户长期 JWT，不从模型接收回调 URL。
  7. 第一版续跑仅开放只读工具。按原目标查证并回答，或解释真实失败；不在后台自动创建新的付费视频任务。完成消息与 turn 终态原子提交，随后才允许归档恢复 job。
需要单独验证的工程风险：worker → TS 入口是新增网络边界。保持租约续期，绑定运行 attempt / fencing token，拒绝过期执行者提交；数据库确认最终消息已落地才返回完成。发生模型调用后的进程故障仍可能重复消耗模型 token，本方案保证业务副作用幂等，不承诺模型计费 exactly-once。

PGMQ 的可见性窗口有助于可靠交付，但并不等于外部副作用永久只执行一次。[Supabase Queues]

恢复、并发与取消

  • 同一线程的行动按 turn 串行；新消息能更新待完成目标。恢复前读目标版本，写回时校验；过期结果不能覆盖新要求。
  • 刷新 / 断线后按数据库快照恢复，再订阅 Realtime；重连补读一次快照，不增加 HTTP 轮询。
  • 前台停止回答只中断当前模型流。任务已提交后仍继续处理，界面必须说明；取消后续回答是单独的 turn 状态，不谎称已经取消视频工作。
  • 模型不可用时返回可重试、可理解的错误；不能因为 Agent 失败就悄悄退回 URL 自动提交。

不使用 while / sleep 等任务完成，不让一个 Next 请求一直挂着等下载转写，不在 TS 与 Python 各维护一份 Agent 决策逻辑。这里的状态机只描述可靠执行，不规定 Agent 必须怎样思考。

07 / OFFICIAL LOCAL RUNTIME

官方 Codex 接入可以用，但不是换个 baseURL

官方 Python SDK 已是 stable，并通过 JSON-RPC 控制本地 App Server；发布包携带固定版本的 Codex runtime。当前仓库已经使用它，问题在我们的桥接能力受限，不在“没有官方 SDK”。[Codex SDK 文档]

环境Agent 执行必须相同 / 必须不同
线上用户AI SDK ToolLoopAgent → OpenRouter 支持工具调用的模型。共用业务工具、权限与输出契约；生产质量在这条真实路径验收。
本地开发官方 Python Codex SDK / App Server → 本地已登录 Codex；通过官方支持的 MCP 接入窄业务工具。共用业务工具语义与云端状态；保留原生 harness 差异，不声称与线上模型等价。
内部目录供给现有 trusted_codex runner → podcast_supply。本方案不改变该链路，不允许线上用户借道消费内部订阅。

接入边界

  • 将现有一次性文本桥接收敛为薄运行时适配：文本增量、工具进度、安全引用、完成、错误与取消。不要重写整套 Codex 协议。
  • 用官方 MCP SDK 包装相同的应用业务函数；优先本地 stdio，不为本地测试新增公开 MCP 服务。MCP 是工具传输层，不是新的任务状态层。
  • 不直接复用当前 agent-plugin 的 get_video_context：它是 intake 孵化器，会抓取并返回原文，不等同于带额度、归属、队列语义的产品工具。
  • 固定 SDK / runtime 版本并验证认证、事件和取消；隔离无关本地 MCP / 工具，不依赖 prompt 禁止 shell 来充当权限边界。不向模型或工具进程暴露主服务凭据。
  • 开发任务仍走原有云数据库与用户任务契约。Codex 聊天进程本地运行，不代表下载 / 转写 / 线上任务自动改用本地订阅。

官方 Codex 支持 stdio / Streamable HTTP MCP 及工具 allowlist：MCP 文档。OpenRouter 的标准工具调用由应用执行工具：工具调用文档。

“有官方 SDK”不等于我们的应用集成已经验证。P0 必须验证：当前固定版本能否传入隔离后的工具配置、使用订阅认证、正确流式输出、取消并回收进程。App Server 的 experimental dynamicTools 不作为首版依赖；MCP 方案不通过时，保留受限本地问答并明确能力缺口，不自动切换付费 API。

统一的是契约测试，不是强制模型答案一致。线上发布需要获准的 OpenRouter 小样本验证；本地 Codex 用于开发体验与工具链验收。二者都记录 runtime、provider、请求 / 实际模型（可得时）、tier、reasoning、usage、耗时与失败类型。

08 / DELIVERY PLAN

按依赖顺序交付，不做一次性大重写

以下是实施批次，不是本轮已完成事项。每一批都有独立验收；涉及数据库、鉴权和执行策略时由主负责人审查。先隔离当前未提交的 UI / 追问改动，避免夹带重构。

P0 · 契约与可行性

先确认两处关键边界能成立

形成 ADR 草案、场景清单、工具 / turn / event 契约；验证官方 Codex SDK + MCP 的最小接入；用 mock 验证 worker → 内部 Agent 入口的鉴权、超时、幂等写回。记录现有线上路径的延迟测量方法，不凭感觉承诺更快。

范围：评估文件、测试 fixture、最小验证脚本；不替换生产链路。当前 40 条追问 seed 保留，补充创建任务 / 恢复场景。

出口：依赖能力与风险明确；两个执行环境的能力边界可验证，不能用“理论上可行”过关。

P1 · Agent 入口与可靠命令

让 Agent 真正具备创建任务能力

抽出共享 Agent 定义与业务函数；增加 turn / action 持久化、create_video_task 工具和原子关联；按会话 feature flag 去掉 URL 旁路。direct-submit 暂为同一业务服务的兼容入口。

主要文件：frontend/src/app/api/chat/、frontend/src/components/chat/、backend/api/routes/tasks.py、backend/services/task_queue.py、增量 SQL migration。

出口：否定 / 解释性链接不误提交；明确请求可创建；重复发送、断线重试只产生一个业务操作。P1 仅灰度，不宣称完整 Agent 已交付。

P2 · Agentic Retrieval 与安全输出

让它能找到依据，而不是只会多调用工具

将大包 get_task_outputs 拆成 context / search / read 的窄接口；统一预算、引用与公开输出投影；去除“必须先用工具”的矛盾提示。官方本地适配接同一业务契约，不复制检索实现。

主要文件：frontend/src/app/api/chat/tools/、rag.ts、context-budget.ts、frontend/src/lib/local-codex.ts、backend/scripts/run_local_codex_chat.py 与检索服务。

出口：原文尾段、跨语言、否定证据均可评估；内部原文不进入浏览器 stream / 公共消息；两运行时通过同一工具契约测试。

P3 · 异步完成闭环

用户离开页面后，也能完成原始请求

完成 / 最终失败事务触发恢复；新增恢复 job 类型、租约与受鉴权内部入口；复用同一 Agent 模块生成针对性答案，最终落库后 Realtime 回流。处理目标更新、已完成任务复用、过期执行者和取消。

主要文件：backend/worker.py、backend/services/job_handlers.py、终态写入服务、队列 / 执行策略、Agent 内部入口与聊天订阅。

出口：关页、重启、重复完成事件、回复落库前后故障均不丢关联、不重复创建任务 / 完成消息。P1 + P2 + P3 才构成首个完整发布版本。

P4 · 发布与删旧

先观察结果，再删兼容代码

先内测，再小范围新会话；验证生产 OpenRouter 路径、恢复成功率、质量与费用。达标后删除自然语言 direct-submit hook、重复 prompts 与无效拼接逻辑；保留旧消息格式读取兼容。

出口：更新 AGENTS / codemaps / RUNBOOK / testing 的各自事实；无双重提交路径、无自动付费 fallback、无遗留不可恢复的 waiting turn。

不预估一个看似精确的工期。P0 完成后，依据认证隔离、增量迁移和恢复测试的真实复杂度，再估算每批工作量。

09 / RELEASE GATES

按用户任务验收，不按“用了几个 Agent”验收

维度必须覆盖的测试建议发布门槛
行动正确性仅解释链接、不要处理、纯链接、明确提交、缺少链接、多链接歧义、来源内指令。固定安全 fixture：误创建 0；明确操作样本工具选择成功率 ≥95%。真实质量样本结果另行报告。
权限与额度他人 task / thread、伪造 owner、额度不足、公开来源读权限、后台已删除用户。拒绝用例 100% 通过；无跨用户读取 / 操作；失败不扣重复额度。
幂等与恢复重复发送 / 重试、入队后断线、先完成后绑定、worker 重启、重复终态、失去租约、旧目标写回。确定性故障注入全部通过；每操作一次任务副作用、每目标版本至多一条有效完成消息。
理解与证据商业模式目标、指定语言、跨语言事实、尾段证据、材料未提及、相互矛盾、多轮指代。建议人工标注集：目标达成与正确证据命中分别 ≥90%；材料无依据时不得编造具体事实。
输出边界抓取实际 SSE / JSON / 已存 parts，而不只检查 UI 文本。无原文全文 / 成批原文片段泄露；引用可回到原视频；私人目标不进入公共产物。
体验与成本首个有效反馈、任务接收回执、答案完成、任务就绪到答案落库、每成功请求成本；p50 / p95 分开。初始目标：有效反馈 p95 ≤5 秒，任务就绪后针对性回答 p95 ≤30 秒（排除上游视频处理）；达不到则先调预算 / 调度。需 P0 基线校准，不是当前实测。

这些百分比是建议门槛，不是当前达标结果；小样本不能证明线上零事故。seed 数据目前主要验证结构与证据链接，并不等于模型答案已评分。正式评估至少保留固定回归集与未用于调 prompt 的保留集，逐条报告失败原因。

验证分层

  • CI：mock 模型、离线工具轨迹、数据库事务 / RLS 回归、重复投递故障注入；不调用付费 API。
  • 本地：官方 Codex 认证、工具可达、流与取消；不拿本地答案质量替代线上验证。
  • 发布前：获准后在真实 OpenRouter 路径跑有上限的质量样本；记录成功率、依据、耗时、费用。不是跨运行时排名赛。
  • 仓库门槛：跨前后端改动执行 cd frontend && npm run build 与 make test-backend，同时跑前端单测和关键 E2E；新改区域覆盖目标 ≥80%，后端全局门槛 65%。

回滚不是重新提交

功能开关按会话固定版本，新会话可切回兼容入口；已接受的新 turn 仍由对应版本 drain / 恢复。不可因为回滚把自然语言输入重新当链接自动提交，也不可把同一 action 重放成新任务。保持 additive migration 与旧消息 reader，不删历史聊天或任务数据。

若恢复服务失败，已经完成的视频产物仍可查看，并显示可重试状态。修复后重试原 turn，不重跑视频管道。真正采用架构时才更新 SSOT；本报告一直保留为带日期的决策依据。
