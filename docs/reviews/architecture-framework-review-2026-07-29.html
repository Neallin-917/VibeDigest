Architecture remediation · 2026-07-30

从双轨产品，收敛为一条 Cloud 主线

本报告是 2026-07-29 架构评审的执行版。桌面/本地产品运行时已从仓库删除， 长任务已从 FastAPI 请求进程迁至 PGMQ + 独立 Worker；依赖、运行时、Docker、 Railway、CI、数据库 schema 与文档也被收敛到更少的事实来源。OrbStack、目标 PGMQ 版本、生产形态迁移与容器运行契约已经完成本地验证；线上环境尚未被本次操作修改。

产品边界：Cloud-only 仓库整改：已完成 本地发布门禁：已通过 生产发布：待远端 CI 审查基线：当前工作区

执行结论

最大的问题不是某个框架版本，而是同一产品同时维护两套运行语义。

判断：当前仓库已经符合 Cloud-first 的最小架构方向。 保留 Next.js、FastAPI、Supabase 与 LangGraph 是合理的；真正需要删除的是 Local/Cloud 双轨、进程内长任务、重复依赖清单、本地生产 Compose、手写类型生成器 和重复 schema 副本。目标 PGMQ 1.5.1、生产旧约束数据形态、非 root Docker 与 Node 24 构建已经验证；生产环境仍需通过远端 CI、应用单一增量迁移并上线 Worker， 不能仅凭本地门禁宣告完成。

目标架构

HTTP 只提交命令；数据库事务保证状态与消息一致；Worker 执行长任务；Realtime 只通知已提交状态。

SupabaseAuth / Postgres / Realtime

原子提交

去重、Guest 配额、任务、输出占位和 pgmq.send 在同一 Postgres 事务内完成；队列失败即整体回滚。

可恢复执行

Worker 使用可见性租约、heartbeat、执行超时、指数退避和最大尝试次数；完成态不会被重试降级，不再依赖 API 进程寿命。

最小消息

消息只携带版本、kind、job id 与实体 id。URL、用户数据和凭据从数据库按需读取，减少泄漏与陈旧数据。

线上 Supabase 发布前快照

2026-07-30 对目标项目完成只读核验；本节记录应用 migration 前的基线。

不可直接迁移

已确认

  • 项目处于 ACTIVE_HEALTHY，Postgres 17；tasks 与 task_outputs 已启用 RLS。
  • 目标项目可用的 PGMQ extension 是 1.5.1，但当前未安装；私有 queue 函数与表不存在。
  • 线上 migration history 只有 13 条旧记录，与仓库 migration 文件名和基线不一致。
  • 线上 tasks 尚无 guest_id；task_outputs.content 仍为 TEXT。
  • 共有 129 个 task / 504 个 output；无孤儿 output；数据库无活动事务或锁等待。

迁移冲突

  • 同一历史 task 有 2 条空的 pending 冗余输出；对应 completed 内容完整，迁移 retention 规则已精确演练。
  • 49 个 pending/processing task 均为 2026-03-24 以前的历史状态；不主动批量改写，新请求按 owner + URL 安全复用。
  • Security Advisor 有 7 项既有 warning；本次安全修复覆盖两个可公开执行的 trigger-only SECURITY DEFINER 函数。
  • 远端 branch API 权限校验不可用，因此以目标 PGMQ 版本的本地生产形态克隆演练替代；生产只应用单一增量迁移，不重放 baseline。

剩余风险与下一步

不建议继续大改框架；下一阶段应把注意力放在真实部署与观测证据。

发布阻断项

  • 远端 migration history 仍保留 13 条历史记录；本次只追加可审计增量，不重写历史，后续再做 metadata repair。
  • asyncio.to_thread 超时不会终止底层线程，当前也没有 attempt fencing；在完成隔离前 Worker 必须保持单副本。
  • 生产 API/Worker 的最小数据库角色、Railway 自定义 config path 与受控真实任务尚未验证。
  • 当前 commit 的远端 PGMQ 与 Docker CI job 尚未执行；本地证据不能替代 GitHub release gate。

非阻断技术债

  • 完整 npm audit 仍受 ESLint/minimatch 开发链影响；production audit 为 0。
  • 开发机默认 Node 仍为 22；本次通过 mise 在 Node 24.18.1 完成正式测试与构建。
  • 失败任务目前以 terminal state + archive 收敛，没有独立 DLQ 浏览界面。
  • 访客浏览器没有可安全证明身份的直接 Realtime RLS 路径；保持认证用户路径，除非引入签名 guest token 或后端广播。

Industry Standard 对齐

本次采用的是 transactional outbox 同类原则下的数据库内原子提交边界、 at-least-once 消费与幂等短路，而不是追求“exactly once”口号； 长任务使用独立 Worker，而非 Web 进程后台线程；Next.js Route Handler 保持公开 BFF 边界， Server Component 优先直接读取所属数据源；依赖使用 manifest + lock 的单一事实源； Cloud 配置与开发工具共享同一数据合同。这样更接近 Supabase Queues、FastAPI 长任务建议、 Railway config-as-code 与现代供应链管理的共同实践。
