判断：当前仓库已经符合 Cloud-first 的最小架构方向。 保留 Next.js、FastAPI、Supabase 与 LangGraph 是合理的；真正需要删除的是 Local/Cloud 双轨、进程内长任务、重复依赖清单、本地生产 Compose、手写类型生成器 和重复 schema 副本。目标 PGMQ 1.5.1、生产旧约束数据形态、非 root Docker、 Node 24 构建、GitHub 远端门禁与真实生产任务均已验证。API 与 Worker 使用同一 commit、独立 Railway 服务和独立配置文件，当前生产只保留一条 Cloud 运行语义。

目标架构

HTTP 只提交命令；数据库事务保证状态与消息一致；Worker 执行长任务；Realtime 只通知已提交状态。

原子提交

去重、Guest 配额、任务、输出占位和 pgmq.send 在同一 Postgres 事务内完成；队列失败即整体回滚。

可恢复执行

Worker 使用可见性租约、heartbeat、执行超时、指数退避和最大尝试次数；完成态不会被重试降级，不再依赖 API 进程寿命。

最小消息

消息只携带版本、kind、job id 与实体 id。URL、用户数据和凭据从数据库按需读取，减少泄漏与陈旧数据。

剩余风险与下一步

没有遗留发布阻断项。当前阶段优先产品体验、前端响应、性能与用户可感知的可靠性；低概率且实现繁重的加固项按规模触发，不提前堆叠。

当前阶段的工程取舍

立即处理会造成错误状态、等待感或性能退化的问题；继续保留凭证、数据所有权、付费额度和防数据丢失等基础边界。 attempt fencing、API/Worker 专用数据库角色、独立 DLQ 控制台和复杂 Guest Realtime 身份体系暂不建设， 仅在 Worker 需要多副本、出现重复执行、安全事件、敏感数据要求或真实用户量证明其必要性时启动。

已知运行约束

  • 远端 migration history 仍保留 13 条历史记录并追加本次增量；未重写历史，后续可做 metadata repair。
  • asyncio.to_thread 超时不会终止底层线程，当前没有 attempt fencing；产品保持单 Worker 副本，扩容到多副本前再实现隔离。
  • API/Worker 目前仍引用既有生产数据库连接；专用最小权限角色作为规模化加固项暂缓，不阻塞产品迭代。

非阻断技术债

  • 完整 npm audit 仍受 ESLint/minimatch 开发链影响；production audit 为 0。
  • 开发机默认 Node 仍为 22；本次通过 mise 在 Node 24.18.1 完成正式测试与构建。
  • 失败任务目前以 terminal state + archive 收敛；独立 DLQ 浏览界面等出现实际运维负担后再建设。
  • 访客浏览器没有可安全证明身份的直接 Realtime RLS 路径；先以真实 Guest 体验验证需求，不提前引入复杂身份体系。
  • 两个既有 extension 位于 public schema，Supabase 泄露密码保护未启用；记录为平台加固项，不挤占当前体验与性能工作。

Industry Standard 对齐

本次采用的是 transactional outbox 同类原则下的数据库内原子提交边界、 at-least-once 消费与幂等短路，而不是追求“exactly once”口号； 长任务使用独立 Worker，而非 Web 进程后台线程；Next.js Route Handler 保持公开 BFF 边界， Server Component 优先直接读取所属数据源；依赖使用 manifest + lock 的单一事实源； Cloud 配置与开发工具共享同一数据合同；首屏图片遵循 Next.js 16 的 loading / fetchPriority 语义，不使用已弃用的 priority，并把高优先级限定为单一 稳定候选。这样更接近 Supabase Queues、FastAPI 长任务建议、 Railway config-as-code 与现代供应链管理的共同实践。
